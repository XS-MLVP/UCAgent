    母工作流执行架构与阶段二次开发¶

    本篇用于指导开发者修改当前 Workflow Builder 母工作流的阶段结构和端到端调用链。Workflow Builder 使用“需求提取、中心设计、分组件生成、集成验收”的结构生成业务工作流；中心设计位于 wfgen/，最终公开产物位于 workflow/。理解这些运行结果是为了安全调整母配置、阶段 Checker 和生成调用顺序，不是让读者手工执行某个子阶段。

    二次开发目标¶

    典型任务包括增加或合并母阶段、调整阶段输入输出、改变中心 workflow spec、接入新生成器、改变评估阻塞策略、优化上下文读取或修复增量终止条件。每项修改都要从母配置进入，沿 UCTool 到 core，再到生成文件和 Checker，形成闭合影响分析。

    母工作流修改入口¶

    • 主构建阶段：根 config.yaml 与 Guide_Doc/stages/。
    • 增量阶段：根 inc.yaml、增量 GuideDoc 和 tools/workflow_evaluation_control/。
    • 评估阶段：eval_tools.yaml、eval_checkers.yaml、eval_flow.yaml、eval_env.yaml、eval_run.yaml。
    • 构建执行：tools/workflow_builder/core.py 及其 uc_tools.py 包装。
    • 启动编排：根 Makefile。

    修改阶段时先画出旧阶段的 reference、output、工具和 Checker，再设计新结构。直接在 YAML 中插入一个 stage 而不更新计划标记、GuideDoc、变量、Checker和回归，会让流程形式存在但无法稳定执行。

    阶段执行¶

    根 config.yaml 定义母工作流阶段。每个阶段包含任务描述、参考文件、输出文件、工具和 Checker。Agent 先通过 RoleInfo 获取当前任务，再读取本阶段必要参考，调用工具生成或更新产物，最后由 Checker 验证。Checker 失败会令同一阶段重试，因此任务描述必须给出准确修复方向，避免 Agent 反复猜格式。

    一个阶段的 reference 不能指向未来阶段才生成的文件。目录也不能作为 reference 或 output 的替代，因为 UCAgent 的引用追踪、权限和存在性判断以具体文件为单位。

    评估数据流¶

    静态评估分为 tools、checkers、flow、env 四个责任域。每个评估 Agent 读取紧凑执行指南、当前报告索引、用户资源和目标源码，然后通过结构化存储追加 checks/findings。聚合器不重新判断源码，只汇总各分项报告和审批状态。

    eval_run 是可选的昂贵运行评估，与静态评估分开。静态审查不得偷偷启动完整子工作流，运行评估也不应一次同时跑 default 和 inc 两种模式。

    控制台¶

    控制台由 tools/workflow_evaluation_control/review_server.py 提供本地 HTTP 服务。页面读取结构化 JSON、构建设计 YAML/Markdown、工作流文件树和 UCAgent 状态。写入操作必须经过服务端校验，浏览器不能直接写原始文件。

    扩展原则¶

    增加阶段前先判断是否能并入现有核心阶段。过多 spec、清单和认知核验会消耗上下文但不增加业务质量。优先保证工具、Checker、GuideDoc、config 和用户文档正确；只有新的结构能消除真实歧义或支持确定性验证时才引入。

    def validate_build_config(data: dict[str, Any]) -> None:
    for key, expected_type in REQUIRED_FIELDS.items():
        value = get_nested(data, key)
        if not isinstance(value, expected_type):

    validate_workflow_spec_contract(data)

    加载函数只接受 YAML mapping，避免后续代码在 list 或标量上产生难懂的属性错误。get_nested() 使用点路径读取必需字段，使错误能直接指出 workflow.name 或 runtime_contract。validate_build_config() 先验证外层形状，再检查语义约束，最后进入中心 workflow spec 验证。开发者新增字段时，应判断它是 Builder 运行不可缺少的必需字段，还是可选业务扩展；把所有字段都塞进 REQUIRED_FIELDS 会破坏旧设计兼容。

    根级 tmp 约束体现了临时文件治理：所有组件共享一个受控临时根，禁止重新引入 .workflow/temp。这类跨组件不变量必须在最早的中心校验中阻断，而不是依赖后期文档提醒。

    中心 workflow spec 校验¶

    validate_workflow_spec_contract() 要求 Checker 和阶段在构建前完整规划。它先收集 shape errors 并一次报告多个结构缺项，再检查名称、源码入口、fixture、测试和阶段引用。这种“一次报告全部同类结构问题”的策略减少 Agent 每次只修一个字段造成的重试。

    核心逻辑可以概括为：建立 Checker 名称、文件、类和 fixture 的唯一集合；验证每个 stage 引用的 Checker 都能在中心定义中找到；验证 reference/output 是具体文件且不存在未来引用；验证阶段注册参数与定义可追踪。若要增加 Checker 字段，不仅要在这里验证，还要同步 checker generator、schema、最小示例和控制台结构视图。

    这一阶段不能验证所有业务语义。例如“章节一致性 Checker 是否真的覆盖用户需求”需要 fixture 和评估流程判断。中心校验负责证明设计闭合和可物化，不应膨胀为运行整个业务。

    顺序很重要。路径安全检查发生在任何写入之前，避免部分产物已经创建后才发现 root 越界。目录先于文件创建；公开与内部文件都通过同一模板分派和 write_file()，因此 overwrite、报告记录和路径边界一致。业务 Checker 在基础骨架和 config 存在后生成，因为 checker generator 需要写源码、fixture，并可能读取注册结构。

    模板分派函数 render_file_by_template() 是固定交付物的集中入口。新增模板时要明确未知模板的行为。目前未知模板会生成空文件并追加 warning；对于强制业务产物，仅靠 warning 通常不够，后续 acceptance 必须阻止空壳通过。不要在多个分支用同一路径生成不同语义内容，否则路径规则会掩盖 template 错误。

    配置生成与阶段注入¶

    源码位置：tools/workflow_config_generator/core.py，符号 validate_config_spec()、_inject_planned_stage_contracts() 和 generate_config()。

    配置生成器先验证 placeholder、作用域泄漏、父工作流路径泄漏、正文详细度以及 reference/output 文件契约。_planned_stages() 把中心 workflow spec 转为按阶段名索引，_inject_planned_stage_contracts() 再把 Checker、参考和输出约束注入 config spec。这样 config 不应成为第二套人工维护的阶段事实来源。

    生成后 _validate_generated_config() 再审查最终 YAML，而不是假设 spec 正确就等于渲染结果正确。开发者修改模板覆盖或 placeholder 语法时，必须同时考虑生成前静态分析和生成后结果验证。常见错误包括未定义变量、双花括号残留、循环替换、父工作区绝对路径、目录被写入 file list，以及 reference 在当前阶段尚不存在。

    增量部署调用链¶

    源码位置：tools/workflow_evaluation_control/incremental.py，符号 deploy_incremental_changes()。

    部署器依次验证工作流根、change id、当前 run/batch/attempt、审批新鲜度、映射字段、候选路径、目标路径和审批覆盖。随后进行 projected semantic audit，保存每个目标旧版本，使用同目录临时文件原子替换，并写 applied_changes.json。中途失败时按逆序 rollback。

    文件生产者与消费者矩阵¶

    文件 生产者 主要消费者 允许更新时机
    requirements_manifest.yaml 首阶段需求提取 计划、构建设计、控制台 需求决策变化时追加同步
    workflow_implementation_plan.md 所有构建阶段 后续阶段、开发者 每阶段只写自己的标记区
    workflow_build.yaml 设计阶段 Builder、各生成器、控制台 物化前完成中心闭合
    config.yaml config generator UCAgent 默认业务流程 构建或批准增量时
    eval/*.json 结构化存储 控制台、聚合、增量 通过受控 CRUD
    applied_changes.json deployer 验收、版本管理 仅实际部署成功后

    这个矩阵用于判断“应该改哪个文件”。例如工具源码和 workflow build spec 不一致时，不能只编辑注册后的 config；应先决定中心设计是否改变，再重新物化或以增量报告完整记录偏差。

    扩展阶段的决策方法¶

    新增阶段需要满足至少一个条件：它产生独立、可验证、被后续消费的产物；它拥有不同写入权限；或它隔离了高成本/高风险动作。单纯因为任务描述很长，不足以拆阶段。拆分后还要计算新增 reference、Checker、GuideDoc 和上下文读取成本。

    反过来，工具生成和工具测试可以在同一责任阶段批量完成：先独立生成多个工具，再一次更新注册和运行综合检查。把每个工具拆成“生成、读回、检查、再读回”四个阶段会放大模型往返，却没有增加确定性证据。

    失败路径与部分写入分析¶

    构建主链的异常可能发生在中心配置加载、路径检查、目录创建、模板渲染、文件写入、Checker物化或示例复制。开发者应确认每一层错误是否带责任域错误码，以及失败时 report 是否准确反映已经发生的写入。Builder 当前不是一个跨全部文件的数据库事务，因此中途失败可能保留已创建文件；重试依赖 overwrite 和各生成器幂等性恢复。

    这意味着新增生成步骤不能假设工作流根总为空。它应验证已有目标、采用安全覆盖策略，并在失败前不要破坏用户漂移文件。对于必须整体一致的共享文件，例如 config 注册，应先在内存生成和校验完整候选，再原子写入，而不是循环追加后在最后一项失败。

    UCTool 包装层应捕获已知 WorkflowBuildError 并返回 code/message/report；未知异常保留 traceback 给开发日志，同时向 Agent返回不含敏感内容的失败摘要。不要捕获所有异常后返回 ok=True 加 warning，这会让阶段 Checker面对半成品并产生误导重试。

    运行契约与示例目标¶

    runtime_contract 连接构建设计和最终 Makefile。它定义 input root、output root、example target 和 required input。Builder据此复制 test_input 到业务工作流示例、生成 input/output 文档，并让 make check_example 检查同一契约。若某个生成器自行假设 data/ 或固定目标名，就会与 config 和文档分叉。

    新增输入类型时，应先更新 runtime contract 和 input example manifest，再让 Builder复制实际样例，最后由 Makefile和 Checker读取同一列表。示例目标必须代表真实最小业务，不能只放空 JSON 为结构检查提供假通过。

    可观察性与阶段耗时¶

    流程层应把关键产物写入 report 或计划，而不是只在 TUI打印。长阶段排障需要知道当前处理的 spec、最近写入、检查返回码和剩余队列。批量生成时先记录队列总数和已完成 id；上下文压缩后从结构化进度继续，不重新全文认识整个工作流。

    性能优化不能删除最终综合检查。正确方式是减少重复全量检查、限制无关读取和并行无共享写入的任务。任何优化都用不同业务对比阶段失败次数、工具调用数、上下文压缩和最终质量。

    主工作流 24 个阶段逐步说明¶

    下面的阶段顺序来自根 config.yaml，是当前母工作流的公开执行架构。WorkflowPlanAppender 几乎贯穿所有阶段，用于只追加当前阶段的设计记录；表中只额外列出本阶段具有代表性的工具。二次开发者修改阶段时必须同时核对 config、对应 Guide_Doc/stages/、实现计划 block、reference/output 和 Checker 参数。

    第一组：需求与中心设计¶

    步骤 主要目的 关键产物与检查 二次开发注意事项
    00 extract_requirements_and_plan 把用户 guide.md 和样例输入转为规范化需求、输入示例 manifest 与完整实现计划。这里决定后续工具、Checker、文档、环境和迁移目标，计划详细度必须高于用户原文。 输出 requirements_manifest.yaml、input_example_manifest.yaml、workflow_implementation_plan.md；由 requirements、input example、implementation plan 和 living plan Checker共同检查。 新增需求字段要同步 manifest schema、最小示例、首阶段 GuideDoc、Checker 和控制台解析。不要把后阶段才能确认的实现结果伪装成用户需求。
    01 design_workflow_build_config 形成唯一中心 workflow_build.yaml，把目录、公开/内部文件、runtime contract、工具、业务 Checker、GuideDoc、环境和 acceptance 组织为可物化设计。 输出中心 build config 和本阶段计划记录；WorkflowBuildConfigChecker 与初始需求覆盖检查验证结构和需求映射。 修改中心 schema 是高影响变更，需要同步 Builder、四类 generator、设计编辑器和 delivery contract。reference 必须是当前存在的具体文件。

    阶段 00 的核心不是“写三份文件”，而是建立后续阶段不再随意重设计的事实来源。若需要增加知识库、许可证或新配置类型，先在这里定义交付契约。阶段 01 则把需求转换成生成器能消费的字段；新增顶层字段前应先判断现有 workflow_spec、runtime_contract 或 acceptance 是否可以表达，避免 spec 膨胀。

    第二组：初始骨架与 Tool 冒烟闭环¶

    步骤 主要目的 关键工具与检查 二次开发注意事项
    02 build_initial_template 使用 WorkflowBuilder 一次创建工作流骨架、环境设施、内部 Checker、中心业务 Checker spec/fixture 和最小公开文件。 WorkflowBuildOutputChecker 检查 21 类初始输出，requirement coverage 防止骨架漏掉用户必需交付物。 修改 Builder 模板分派、固定目录或环境文件时更新本阶段 output 清单和构建回归。不要在后阶段补本应由骨架固定生成的文件。
    03 verify_tool_generation_loop 验证 Tool generator 本身能够从 spec 生成源码、注册、测试并维护 generation state，先打通通用循环再生成业务 Tool。 使用 WorkflowToolGenerator；WorkflowToolGenerationChecker 检查 spec、源码、注册和测试闭环。 新增 Tool 模板或覆盖策略先在这里用小 fixture 验证。共享注册和 generation state 必须串行写。
    04 design_smoke_business_tool_spec 从用户业务工具中选择最小但有代表性的 smoke Tool，设计真实参数、输出、错误和测试 spec。 输出 smoke tool spec 和计划记录；WorkflowGeneratedToolChecker 此时重点验证 spec 质量。 选择的 Tool 应覆盖关键库或输入格式，但不能复杂到阻塞整个母流程。修改选择规则时更新 smoke baseline 语义。
    05 implement_smoke_business_tool 通过 WorkflowToolGenerator 物化 smoke Tool，证明母生成器能产生真正可 import、可注册的业务实现。 输出工具源码和 generation state；Checker验证源码、注册、正常/失败调用。 不允许母 Agent绕过生成器手写正式源码。新增 renderer 后要在此阶段验证模板结果，而不是只测 renderer 字符串。
    06 strengthen_smoke_business_tool_tests 在初次实现基础上补边界、异常、重复运行和路径安全测试，防止“只有一个 happy path”伪通过。 更新 tool spec、case 和状态；同一 WorkflowGeneratedToolChecker 用 strengthened 参数检查更强覆盖。 强化测试应一次改变一个条件。修改强度门槛时避免要求所有业务工具具有不相关测试。
    07 initialize_smoke_workflow 把最小工作流配置、setup、Makefile 和运行目标整合起来，运行环境预检并建立可启动 smoke workflow。 使用 WorkflowEnvironmentPreflight、必要 Tool 生成和 ChildWorkflowSupervisor；minimal init 与 environment setup Checker验证。 这里连接生成与运行环境。新增 Make 目标、环境变量或代理策略要同时改 Builder模板、schema、GuideDoc 和环境回归。
    08 verify_generated_tools_through_mcp 从 UCAgent 实际 MCP/adapter 边界调用生成 Tool，证明不是只能在 Python direct runner 中使用。 生成 MCP 测试日志/报告；WorkflowMCPToolIntegrationChecker 检查注册、调用和结构化结果。 修改 adapter、--ex-tools 或 MCP 参数后必须更新此阶段。不要用普通函数调用代替 MCP 集成证据。
    09 freeze_smoke_baseline 把已经通过的最小工具、配置、测试和环境形成 smoke baseline，作为后续全量生成的稳定参照。 输出 smoke manifest 和计划记录；requirement coverage 类 Checker核对 baseline。 baseline 只冻结已验证事实，不应包含未来全部业务工具。修改字段时提供旧 manifest 兼容或迁移。

    这一组采用“先验证生成器，再生成一个业务 Tool，再从真实边界调用”的递进设计。二次开发时不要把 03、05、08 合并成一个无法定位失败的大阶段；也不要为每个 Tool复制整套 smoke 阶段。全量工具在后面的批量阶段处理。

    第三组：完整配置与全部业务 Tool¶

    步骤 主要目的 关键工具与检查 二次开发注意事项
    10 design_complete_runtime_configs 根据中心 spec 设计最终默认流程、增量流程及可选评估配置，明确所有变量、阶段、GuideDoc 和 Checker注入。 输出 config specs 与计划记录；本阶段主要由 living plan 保证设计追加。 增加 config 类型时先更新 requirements 和 workflow build schema，禁止恢复已取消的 default/empty 配置。
    11 generate_complete_runtime_configs 使用 WorkflowConfigGenerator 生成真实 YAML，并通过 WorkflowArtifactInspector 自审 placeholder、路径、reference 时序和注册。 输出 config.yaml、config/inc.yaml 等及审计；WorkflowRuntimeConfigAuditChecker 阻止未知变量和错误引用。 修改 placeholder 规则、阶段注入或 file contract 必须同时更新 config generator 的生成前和生成后校验。
    12 design_all_business_tool_specs 按 requirements 和实现计划为除 smoke 之外的全部业务 Tool 建立完整 spec 队列。 输出 tool specs/manifest 和计划记录。 应复用 smoke 已验证的接口模式，但每个工具仍要有业务算法、异常和测试。避免在本阶段写源码后跳过生成器。
    13 generate_all_business_tools 批量使用 WorkflowToolGenerator 生成全部业务 Tool，并一次协调共享注册和状态。 输出工具源码、注册与 generation state。 独立源码可并行规划，共享 config/state 串行提交。新增工具必须与 requirements、spec、docs 一致。
    14 run_full_tool_test_suite 对所有工具运行 spec、静态 import、direct cases 和 MCP 集成，形成全量测试报告。 输出工具测试汇总；full_mcp_tool_integration_check 检查不是只测 smoke Tool。 修改测试 runner 时保留单工具定位信息和总返回码。不要每生成一个文件就重复全套测试。

    10–11 把“设计配置”和“生成并自审配置”分开，是为了在任何正式 YAML 写入前发现中心设计矛盾。12–14 同理先完成 Tool spec 队列，再批量物化和综合测试。若新业务只有一个 Tool，这些阶段仍应保留语义，但任务可以快速确认没有额外项，而不是生成空壳文件凑数量。

    第四组：文档、依赖和可复用模板¶

    步骤 主要目的 关键工具与检查 二次开发注意事项
    15 design_all_document_specs 规划全部 GuideDoc、用户 docs、开发者源码分析和依赖说明，建立文档 spec。 输出 GuideDoc spec 集；WorkflowGuideDocSpecChecker 验证章节、路径、长度和覆盖。 新增文档类型应更新 guidedoc schema、生成器和文档回归。FAQ 只记录跨业务已确认经验。
    16 generate_all_documentation_and_dependencies 使用 WorkflowGuideDocGenerator 生成 GuideDoc和用户文档，同时完成 requirements/system dependency 声明。 输出 GuideDoc、docs、requirements；Generated GuideDoc、User Docs 和 Dependency Checker分别检查。 用户文档与 Agent GuideDoc不能混注册。开发者文档必须读取最终真实源码后分析，不能停留在计划模板。
    17 generate_all_reusable_templates 使用 WorkflowBuilder 的受控模板能力生成用户可复制输入模板、资源结构或业务复用文件。 输出 reusable template manifest/文件和计划记录。 模板必须来自需求，放在公开约定位置；临时 fixture不能伪装为用户模板。未知模板名必须在物化前检查。

    第五组：发布完整性与最终需求覆盖¶

    步骤 主要目的 关键产物与检查 二次开发注意事项
    18 complete_readme_and_makefile 汇总最终命令、输入输出、环境、测试和 tmux 目标，确保 README 与 Makefile反映实际交付。 更新 README、Makefile、setup相关文件和计划。 修改生成 Makefile target 时同时更新 README、QuickStart、环境 schema 和 acceptance。
    19 mark_feature_complete 在所有计划功能已物化后写 feature completeness 状态，禁止后续用“计划中”掩盖漏项。 输出 feature complete manifest/状态和计划记录。 完成状态必须来自实际文件和测试，不可仅根据阶段编号。新增交付类别要加入完成计算。
    20 verify_final_requirement_coverage 将最终 workflow 文件、工具、Checker、配置和文档重新映射回每条用户需求，发现遗漏或语义偏离。 输出最终 coverage；WorkflowRequirementCoverageChecker 按 final 模式检查。 修改 coverage 算法时保留 requirement ref 到真实文件/证据的映射，不能只比较数量。

    第六组：清理、迁移与外部验证¶

    步骤 主要目的 关键工具与检查 二次开发注意事项
    21 clean_release_candidate 使用 WorkflowArtifactInspector 清除临时日志、浏览器 profile、缓存和未登记文件，同时保留公开交付和必要内部测试。 输出清理报告和计划记录。 clean 白名单/保留规则变更要运行 write boundary；绝不删除 eval、res、input 或版本历史。
    22 prepare_and_verify_migration_packages 构建完整/部分迁移包及 manifest，验证包内路径、依赖和允许内容。 输出迁移包、manifest、检查报告；WorkflowMigrationPackageChecker 验证生成包。 部分包禁止意外包含 Tool/Checker；完整包必须覆盖环境、docs、示例和安装器。修改包格式要提供版本。
    23 verify_migrated_release 在隔离目标中解包、配置并验证迁移后的工作流，而不是只检查压缩包文件名。 输出最终迁移验证报告；同类 Migration Checker以 final 参数检查安装、路径和测试。 验证环境不得依赖原工作区绝对路径。新增安装步骤时更新 installer、manifest 和此阶段命令白名单。

    如何二次开发一个阶段¶

    1. 在根 config.yaml 中确认阶段唯一职责、位置和 alias。
    2. 修改或新增对应 Guide_Doc/stages/<index>_<name>.md，给出工具、Checker和最小格式。
    3. 若阶段产生新的中心文件，更新 wfgen schema、设计编辑器和实现计划标记。
    4. 在 reference_files 中只列阶段开始前存在的文件，在 output_files 中只列本阶段实际写入文件。
    5. 注册适合的 Checker；新 Checker走 03 文档描述的生成和回归路径。
    6. 更新 living plan 规则，保证本阶段只追加自己的 block。
    7. 增加配置/GuideDoc/阶段回归，并在一个全新业务工作区验证。

    新增阶段后不要只观察它能否通过，还要比较前后阶段上下文是否重复、是否引入新的全量文档读取、是否可以合并到已有责任域。阶段删除则必须清理 Checker alias、GuideDoc、计划标记、reference 和所有恢复历史中的旧阶段假设。
