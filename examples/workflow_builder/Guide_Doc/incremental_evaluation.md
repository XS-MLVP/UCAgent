# 评估驱动增量修改详细指导

## 文档目的
本指导用于执行可审计的工作流评估。规则不是关键词搜索清单，而是从声明、实现、调用、产物、检查和用户需求建立闭环。
评估者必须读取完整文件和上下文，不能根据搜索片段直接下结论，也不能为通过评估而修改被评估工程。
每条规则都要保留可复现证据。无法获得证据时使用 blocked 或 suspected，不允许猜测通过。

## 严重程度
- critical：导致UCAgent无法启动、必然卡死、无限重试、破坏文件、越界访问、泄漏秘密或用假成功掩盖整体失败。
- high：核心用户需求没有实现、关键工具不可用、关键Checker漏检、重要产物错误或工作流欺骗用户已经完成。
- medium：部分覆盖不足、可恢复契约错误、限定环境的兼容问题或具有条件性的错误结果风险。
- low：不影响正确运行的文档、维护性和非关键一致性问题。
- info：经过核实的观察项，不构成当前缺陷。

## 证据与反证
- confirmed必须有确定性复现或能直接证明结论的源码与数据流证据。
- probable至少需要两项相互独立的证据，并明确尚未完成的验证。
- suspected只进入待确认记录，不得直接成为正式finding。
- 每个candidate finding提交前都要尝试寻找合法替代解释，并重读精确源码、配置字段和调用方。
- 检查通过也要记录对象、方法和证据，禁止只写“已检查”。

## 最小可通过报告
- contract_version必须为2。
- checks必须包含本评估类型全部强制ID。
- 每个check必须包含id、status、summary和非空evidence。
- finding必须包含expected、actual、severity_reason、confidence、requirement_refs和结构化evidence。
- source证据至少包含kind、path、location、observation；command证据至少包含kind、command、returncode、observation。
- artifact证据至少包含kind、path、observation；timeline证据至少包含kind、time、observation。
- 任一critical/high或强制检查失败时报告状态必须为failed。
- 仅有medium/low时状态使用passed_with_findings。
- 证据不足时状态使用blocked。

## 批准到文件的授权链
- 用户问题说明、改进建议和补充信息本身都是待评审条目，只有对应 approvals 记录为 approved 后才能授权修改。
- rejected 表示明确不实施，deferred 表示等待更多信息；两者都不得作为 IncrementalChangeDeployer 的 approval_ids。
- 批量批准只是一次写入多个独立决定，每条决定仍保存自己的 source_id、source_fingerprint 和审计历史。
- 每个部署 mapping 必须包含 source、target、approval_ids 和 rationale，不能只在部署顶层笼统引用批准。
- mapping.approval_ids 必须是当前部署 approval_ids 的非空子集，并且其中每项仍是当前有效批准。
- mapping.rationale 至少二十字符，应解释为什么该文件是满足对应批准项所必需的，而不是重复文件名。
- 一个批准可以授权多个有直接关系的文件，例如实现、契约、测试和开发者文档，但每个文件都要独立说明关系。
- 多个批准可以共同授权同一文件，但不能引用与该文件无关的批准来扩大修改范围。
- 部署顶层列出的每个 approval_id 必须至少被一个 mapping 使用，禁止夹带未实际处理的批准制造完成假象。
- 部署前必须完成所有 mapping 的路径、批准、理由和候选存在性预检，预检失败时不得先复制部分文件。
- 部署记录必须在 applied_changes 中逐文件保存批准列表、理由和 SHA256，供 IncrementalApprovalChecker 反向核验。
- 工具只能证明授权来源、文件关联和字节一致性，不能自动证明自然语言语义已经完全满足。
- 语义是否满足必须通过受影响的确定性测试、对应评估器复评和用户验收共同确认。
- 修改完成后 finding 只能进入 fix_applied_pending_recheck，不得因为部署成功直接标记 resolved。
- 若批准条目的内容、状态或指纹发生变化，旧决定立即失效，必须重新审批后才能授权新的部署；已经完成的历史部署仍以部署时保存的 approval_provenance 作为审计证据。

## 规则目录
### 01. INC-AUTHORIZATION：修改没有明确批准
- INC-AUTHORIZATION检查对象：approvals决定、理由和来源。
- INC-AUTHORIZATION风险说明：如果该规则失败，可能出现“开放问题或建议被自动实施”，评估者必须分析它对启动、进度、产物和用户语义的真实影响。
- INC-AUTHORIZATION使用工具：优先使用YAML/JSON解析器、Python AST、受控静态审计工具和EvaluationCommandRunner；禁止用模糊关键词搜索代替结构化检查。
- INC-AUTHORIZATION操作步骤一：从中心规划或用户需求定位声明，再向配置绑定、源码实现、测试和实际产物正向追踪。
- INC-AUTHORIZATION操作步骤二：从最终产物或运行入口反向追踪到生产者，确认没有孤立实现、隐式假设或未声明依赖。
- INC-AUTHORIZATION通过条件：声明、实现、调用、产物与验证相互一致，并有独立证据证明不会发生“开放问题或建议被自动实施”。
- INC-AUTHORIZATION失败条件：发现确定矛盾、最小反例可复现，或者关键证据缺失到无法证明工作流可正确完成。
- INC-AUTHORIZATION正确示例：报告列出精确文件和字段、预期行为、实际结果、受控命令返回码，并解释为什么满足“修改没有明确批准”。
- INC-AUTHORIZATION常见错误示例：仅写“看起来正常”或只引用搜索片段；这种记录不能证明“approvals决定、理由和来源”已经得到验证。
- INC-AUTHORIZATION证据要求：至少给出一个可定位源码或配置证据；涉及行为时再给出独立fixture、命令结果或产物内容证据。
- INC-AUTHORIZATION默认严重程度：critical；若会导致无法启动、卡死、破坏或假成功，升级为critical；若证据不足则标blocked或suspected。
- INC-AUTHORIZATION误报排除：检查框架允许的适配器、路径归一化、明确的顺序refinement和用户声明的支持边界，不得把架构偏好当缺陷。
- INC-AUTHORIZATION修复方向：指出最小责任模块、需要同步的规范/实现/测试/文档以及复评规则，不在评估阶段直接代替工作流修复。
