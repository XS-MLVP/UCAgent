# Codex 使用与实践记录

## 开始任务

进入目标工程目录后，先说明希望完成的结果、不能修改的边界和验证方式。Codex 会读取目录结构、配置和相关代码，必要时先运行现有检查建立基线。

如果任务需要启动 UCAgent 或其他交互式程序，可以在 tmux 会话中运行。观察者可通过只读方式接入，避免误输入影响正在执行的流程。

## 修改与验证

Codex 通常先定位与请求直接相关的模块，再进行小范围修改。修改完成后，应运行语法检查、单元测试、业务 checker 或端到端流程。

对于生成文件的工具，需要特别检查输出路径和重复运行行为。产物应位于命令指定的输出目录，测试不应依赖上一次运行遗留的临时文件。

## 长时间运行的观察

长流程可以每隔一段时间检查一次：

- 当前阶段是否变化
- 连续失败次数是否增长
- 是否长时间停在同一个工具调用
- 输出目录是否出现预期中间产物
- 是否有重复 Agent 或端口冲突

如果一个阶段持续没有进展，应先暂停进程并检查日志，而不是无限等待模型重试。

## 常见故障

工具调用参数错误通常会在日志中留下明确异常。修复工具或临时脚本后，可以从当前阶段恢复，不必删除已经通过的阶段结果。

多个 Agent 共用同一个 MCP 服务端口时，工具注册和调用可能失效。不同进程应使用独立端口，或者在不需要 MCP 服务时显式关闭端口。

历史消息中出现未完成的 tool call 时，后端可能返回 400 错误。此时应先停止当前流程，判断是否能够在保留阶段状态的情况下重新启动。

## 结果交付

完成任务后需要说明：

- 修改了哪些文件
- 生成了哪些产物
- 运行了哪些验证
- 哪些问题已经修复
- 是否仍有未验证风险

工作流类项目还应提供 README、quickstart、可运行示例和迁移安装器，使后续使用者不依赖原开发现场。
