
# Result Analysis and Process Summary

After verification is complete, review the stage status, test reports, and generated files simultaneously. A stage displaying as completed only indicates that the stage's Checker has passed; whether the DUT contains defects must still be determined by combining test assertions, failure logs, and Bug evidence.

## Workspace Structure

Taking `output/` as the workspace and `unity_test/` as the default output directory:

```text
output/
├── Adder/                 # picker exported DUT Python package and input documents
├── Guide_Doc/             # guidance documents copied at runtime
├── unity_test/            # documents, tests, and stage artifacts generated by the workflow
│   └── tests/
├── uc_test_report/        # toffee-test report (if tests have been run)
└── .ucagent/              # configuration snapshots, history, and runtime status
```

The Makefile example uses `output/workspace_<DUT>/` as the workspace, so simply replace `output/` above with that directory.

## Key Artifacts

- `Guide_Doc/`: Runtime reference documents and format examples. It guides the Agent in writing artifacts; it is not a test result and should not be used as verification evidence.
- `unity_test/tests/`: DUT fixture, API, coverage model, and pytest cases.
- `unity_test/*.md`: Documents such as verification plan, basic information, functional points, line coverage, Bug analysis, and summary. The specific files are determined by the workflow.
- `uc_test_report/`: HTML/JSON reports generated by toffee-test (if the current process invoked the UnityChip test tool).
- `.ucagent/runtime_config.json`: Resolved non-sensitive runtime configuration, read by Skill and other runtime scripts; do not write API Keys into it.

For detailed templates and artifact contracts, see [Template Files and Generated Artifacts](../03_develop/04_template.md).

## Recommended Review Order

1. Check `status` to confirm whether there are any incomplete or skipped stages.
2. Open the test reports in `uc_test_report/` to distinguish between test infrastructure failures and reproducible DUT failures.
3. For each failed case, return to the test code, RTL, and specification to check inputs, assertions, logs, and necessary waveform evidence.
4. Read `unity_test/{DUT}_bug_analysis.md` and `unity_test/{DUT}_test_summary.md` (if the current workflow generated these files).
5. After fixing, re-run the relevant tests and invoke `Check`; use `GoToStage` to return to a reached stage when backfilling is needed.

## Preparing Your Own Task

Prepare at least:

```text
<workspace>/
└── <DUT>/
    ├── <top>.v / .sv / .scala
    └── README.md
```

The `<DUT>` directory can also contain filelists, auxiliary RTL, reference models, and other requirement documents. First use picker to export the `<workspace>/<DUT>` Python package, then run `ucagent <workspace> <DUT>`; the Master Launch page can upload and compile on your behalf.

The workflow generates FG/FC/CK functional models, fixtures, APIs, tests, and reports based on these inputs. Output file names are subject to the current configuration's `stage` and Checker; do not assume in advance that a specific Bug, waveform, or coverage file will be generated.
