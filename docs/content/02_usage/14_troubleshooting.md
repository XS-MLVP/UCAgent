
# 运行排障：未启动、暂停与失败

“界面没有回复”不等于模型断线。先确定当前是 single、Global、Super 还是 Sub，再区分启动、执行、验收和收尾。正常等待输入、人工审核或资源配额时，也可能没有新的模型输出。

## 先保存最小现场

- 记录版本/提交、完整启动命令、backend、工作流和错误发生的时间；命令中的凭据必须脱敏。
- single 记录工作区、运行时阶段索引、`status` 和当前 Checker 诊断；阶段编号随工作流变化，不要只报告“阶段 16”。
- multi 记录 session、Agent ID、attempt、`AgentStatus` 的错误和恢复详情；Sub 还要关联父 Super 和任务 ID。
- 保存最后一次成功操作、首个明确错误，以及该次 attempt 的输出路径。不要只截取最后一句模型回复。
- 不要先删除 `.ucagent`、改写 checkpoint 或重用旧回执。不要公开完整配置、`connection.json`、API key、MCP token 或客户端登录文件。

Global 的目录和文件含义见 [状态与证据索引](13_global_agent.md)。single 的操作查询和取消见 [运行控制](10_runtime_control.md)。

## 按失败层次检查

| 现象或证据 | 定位 | 下一步 |
| --- | --- | --- |
| 服务或交互界面打开，但没有执行操作 | 可能正在等待明确请求 | single 检查是否提交 `loop` / `continue`；Global 检查用户消息是否已接收及其操作状态，不反复重复提交 |
| 配置解析、插件发现、工作流准备失败 | 尚未进入正常模型执行 | 根据首个错误检查插件、工作流、输入路径和准备日志；不要先更换模型 |
| `Required workflow MCP tools are unavailable` | 业务 MCP 工具集合预检失败 | 检查完整文件工具开关、过滤配置和插件注册，按 [MCP 接入](../01_start/03_mcp_mode.md) 修复 |
| `CLI configuration validation failed; no model was started` | 命令行客户端配置探测/校验失败 | 检查所选 backend 的 inspect/validate 配置与 CLI 实际配置；不等同于前一行的必需工具缺失，也不是模型网络错误的证据 |
| `Configured CLI executable is unavailable` | 外部客户端不可执行或不在该进程 PATH 中 | 在同一启动环境检查可执行文件路径，不只确认另一个终端能运行 |
| `CLI probe requires...`、probe 超时或非 JSON 输出 | 客户端启动前探测失败 | 检查配置的探测命令、返回格式和超时；避免将探测命令与真实模型调用混淆 |
| CLI 非零退出，或请求日志明确报告连接/认证错误 | 后端执行失败 | 检查该角色私有会话的 `stderr.log`、`stdout.log`，再根据实际错误处理连接、鉴权或客户端配置 |
| Checker 失败但模型仍可调用工具 | 业务验收失败 | 按结构化诊断的 `error_code`、artifact、observed/expected、`next_action` 修复，不把基础设施错误登记为 DUT Bug |
| `ready` 提交被拒绝 | 批次、子阶段或收尾证据未完成 | 继续当前 Sub；按 `CurrentTips.submission` 完成检查、Skill 或 journal，不为下一批重新建 Sub |
| Super 等待审核、预算或外部条件 | 可恢复的暂停，不一定是崩溃 | 按 [多 Agent 的暂停与恢复](11_multi_agent.md#分类处理暂停与恢复) 使用明确的恢复入口 |
| 已提交、正在取消或 CLI 已退出，但任务未成功 | 执行退出、产物校验或最终收尾尚未完成/失败 | 确认工具与进程已经停止，再检查产物摘要和运行回执；不要用零退出码代替 Checker 验收 |

MCP 服务 ready 只证明端点启动，不保证后端认证成功；客户端配置预检成功也不保证下一次模型请求成功。只有具体请求/进程错误才能支持“模型连接中断”的判断。

## 追踪同一条执行链

1. 确认当前角色和失败层次。Global 调度状态、Super 执行状态、阶段状态和 HTTP operation 状态不是同一个状态机。
2. 存活实例先查实时状态；离线分析按同一个 Agent/attempt 关联快照、日志和回执。文件可能来自最后一次刷新，不能单凭修改时间认定进程仍在工作。
3. 业务阶段失败先读 Checker 的有界诊断，再读相应原始输出。`Check` 推进批次不等于阶段完成，Sub 提交也不等于最终验收通过。
4. multi 的 CLI 原始输出保存在每个角色的私有会话中；其路径和业务 cwd 不同，参见 [外部执行](11_multi_agent.md)。不要把 Global、Super 和 Sub 的客户端 session ID 混用。
5. 回执存在仍需经过框架的身份、attempt、阶段与文件摘要复核；不要通过手改 JSON 或复制别次回执“恢复成功”。

## 恢复方式的边界

| 方式 | 保留或改变什么 |
| --- | --- |
| 切换 Console/TUI | 同一运行实例继续存在，不创建新任务 |
| `ucagent attach` | 连接本机已有会话或查看保存状态，不重跑工作流，也不接管失去宿主的进程 |
| `MessageSuper` | 补充指导，不代替正式审核、预算追加或恢复操作 |
| `RecoverSuper` | 按用户明确指令恢复适用的存活暂停任务；可用动作由当前问题类型决定 |
| `RetrySuper` | 对已结束任务创建新 attempt，保留旧记录，不等于原进程原地续跑 |
| 重启 single | 按现有持久化恢复阶段工作，不保证恢复完整模型对话、旧 operation ID 或未结束调用 |

取消采用协作和进程清理机制；“取消请求已接受”不等于写入者已经退出。未确认旧执行停止前，不要对同一工作区再启动另一个执行者。

## 提交问题报告

提供：版本、脱敏启动命令、角色与工作流、阶段标题/索引、Agent/attempt、首个错误、最后成功操作、相关日志片段、预期与实际行为。说明是否发生过配置修改、重试、手工编辑或复用旧工作区。完整日志只在确认无凭据且接收方可信后提供。
