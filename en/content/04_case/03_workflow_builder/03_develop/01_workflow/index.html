    Mother Workflow Execution Architecture and Phase Secondary Development¶

    This document guides developers in modifying the stage structure and end-to-end call chain of the current Workflow Builder mother workflow. The Workflow Builder generates business workflows using the "Requirement Extraction, Central Design, Component Generation, Integration Acceptance" structure; the Central Design resides in wfgen/, and the final published artifacts are located in workflow/. Understanding these execution results is necessary for safely adjusting the mother configuration, phase Checkers, and generation call order, not for readers to manually execute a specific sub-phase.

    Secondary Development Goals¶

    Typical tasks include adding or merging mother phases, adjusting phase inputs and outputs, modifying the central workflow spec, integrating new generators, changing evaluation blocking strategies, optimizing context reading, or fixing incremental termination conditions. Every modification must enter from the mother configuration, traverse UCTool to core, then reach generated files and Checkers, forming a closed impact analysis.

    Mother Workflow Modification Entry Points¶

    • Main Build Phase: Root config.yaml and Guide_Doc/stages/.
    • Incremental Phase: Root inc.yaml, incremental GuideDoc, and tools/workflow_evaluation_control/.
    • Evaluation Phase: eval_tools.yaml, eval_checkers.yaml, eval_flow.yaml, eval_env.yaml, eval_run.yaml.
    • Build Execution: tools/workflow_builder/core.py and its uc_tools.py wrapper.
    • Orchestration Startup: Root Makefile.

    When modifying phases, first draw the reference, output, tools, and Checker of the old phase, then design the new structure. Inserting a stage directly into YAML without updating plan markers, GuideDoc, variables, Checkers, and regression tests will result in a formally existing process that cannot execute stably.

    requirements_manifest.yaml is the normalized requirement list; workflow_build.yaml is the central build design, which must declare phases, files, tools, Checkers, GuideDoc, and execution contracts in advance. The implementation plan facilitates cross-phase communication; subsequent phases can only append questions and handling within their own marked areas and cannot override prior decisions.

    Phase Execution¶

    The root config.yaml defines the mother workflow phases. Each phase contains a task description, reference files, output files, tools, and Checkers. The Agent first acquires the current task via RoleInfo, then reads necessary references for the phase, calls tools to generate or update artifacts, and finally has the Checker verify. If the Checker fails, the same phase retries; therefore, the task description must provide an accurate repair direction to avoid the Agent repeatedly guessing formats.

    A phase's reference cannot point to files generated by future phases. Directories cannot serve as substitutes for references or outputs, because UCAgent's reference tracking, permissions, and existence checks operate on a per-file basis.

    Evaluation Data Flow¶

    Static evaluation is divided into four responsibility domains: tools, checkers, flow, and env. Each evaluation Agent reads a compact execution guide, the current report index, user resources, and target source code, then appends checks/findings via structured storage. The aggregator does not re-evaluate the source code; it only summarizes individual reports and approval statuses.

    eval_run is an optional expensive runtime evaluation, separate from static evaluation. Static review must not secretly launch the full sub-workflow, and runtime evaluation should not simultaneously run both default and inc modes.

Version management addresses recoverability, not re-approving files already deployed.

    Console¶

    The console is provided by tools/workflow_evaluation_control/review_server.py as a local HTTP service. Pages read structured JSON, construct design YAML/Markdown, workflow file trees, and UCAgent status. Write operations must pass server-side validation; browsers cannot directly write raw files.

    Extension Principles¶

    Before adding a phase, determine if it can be merged into an existing core phase. Excessive specifications, lists, and cognitive verifications consume context without increasing business quality. Prioritize ensuring tools, Checkers, GuideDoc, config, and user documentation are correct; introduce new structures only if they eliminate real ambiguities or support deterministic verification.

    def validate_build_config(data: dict[str, Any]) -> None:

        if not isinstance(value, expected_type):

    The loading function accepts only YAML mappings to avoid subsequent code producing hard-to-understand attribute errors on lists or scalars. get_nested() uses dot-path reading for required fields, allowing errors to directly point to workflow.name or runtime_contract. validate_build_config() first validates the outer shape, then checks semantic constraints, and finally enters the central workflow spec validation. When developers add new fields, they should determine if it is a required field indispensable for Builder execution or an optional business extension; stuffing all fields into REQUIRED_FIELDS will break backward design compatibility.

    The root-level tmp constraint reflects temporary file governance: all components share a controlled temporary root, prohibiting the re-introduction of .workflow/temp. Such cross-component invariants must be blocked in the earliest central validation, rather than relying on late documentation reminders.

    Central Workflow Spec Validation¶

    validate_workflow_spec_contract() requires Checkers and phases to fully plan before building. It first collects shape errors and reports multiple structural missing items at once, then checks names, source entry points, fixtures, tests, and phase references. This strategy of "reporting all similar structural issues at once" reduces retries caused by Agents fixing only one field per attempt.

    The core logic can be summarized as: establish a unique set of Checker names, files, classes, and fixtures; verify that every stage reference to a Checker can be found in the central definition; verify that references/outputs are specific files with no future references; and verify that stage registration parameters are traceable to definitions. If adding a Checker field, validation must occur here, synchronizing the checker generator, schema, minimal examples, and console structure views.

    This stage cannot validate all business semantics. For example, "whether the Chapter Consistency Checker truly covers user requirements" requires fixture and evaluation process judgment. Central validation is responsible for proving design closure and materialization, not for inflating to running the entire business.

    Order is critical. Path safety checks occur before any writes to avoid discovering root boundary violations after partial artifacts are created. Directories are created before files; both public and internal files are dispatched via the same template and write_file(), ensuring consistent overwrite, report recording, and path boundaries. Business Checkers are generated after the basic skeleton and config exist, because the checker generator needs to write source code and fixtures and may read the registered structure.

    The template dispatch function render_file_by_template() is the centralized entry point for fixed deliverables. When adding new templates, the behavior of unknown templates must be explicitly defined. Currently, unknown templates generate empty files and append warnings; for mandatory business artifacts, warnings alone are usually insufficient, and subsequent acceptance must block empty shells from passing. Do not generate different semantic content via the same path in multiple branches, as path rules will mask template errors.

    Configuration Generation and Phase Injection¶

    Source location: tools/workflow_config_generator/core.py, symbols validate_config_spec(), _inject_planned_stage_contracts(), and generate_config().

    The configuration generator first validates placeholders, scope leaks, parent workflow path leaks, body detail, and reference/output file contracts. _planned_stages() converts the central workflow spec into a structure indexed by phase names, and _inject_planned_stage_contracts() injects Checker, reference, and output constraints into the config spec. This ensures the config should not become a second set of manually maintained phase facts.

    After generation, _validate_generated_config() reviews the final YAML rather than assuming the spec is correct implies the rendered result is correct. Common errors include undefined variables, double-bracket remnants, loop replacements, absolute parent workspace paths, directories written to the file list, and references to files not yet existing in the current phase.

    Report stages always run to persist failure reasons and suggestions even if preceding stages are blocked, rather than exiting without a report. Explicitly skipped stages take precedence over normal running; blocked and terminated statuses prevent expensive subsequent actions; completed status prevents redundant execution. evaluation_control_action() appends an event for each state change, making the reason for skipping auditable.

    When modifying the state machine, prevent both extremes: running all expensive stages even after blocking, and skipping the report stage even after failure. The evaluation state machine is not a single state set with the incremental deployment state machine; do not directly apply evaluation pending/blocked semantics to an incremental process that has already replaced formal files.

    Incremental Deployment Call Chain¶

    Source location: tools/workflow_evaluation_control/incremental.py, symbol deploy_incremental_changes().

    The deployer sequentially validates the workflow root, change id, current run/batch/attempt, approval freshness, mapped fields, candidate paths, target paths, and approval coverage. It then performs a projected semantic audit, saves each target old version, uses atomic replacement with temporary files in the same directory, and writes applied_changes.json. If failure occurs midway, rollback proceeds in reverse order.

    _atomic_copy() uses os.replace(), so it does not require write permissions on the old file itself, only that the target directory allows creation and replacement. This is precisely why read-only config/Makefile files can still be deployed under control. Backup records include whether the original file exists, its path, hash, and timestamp, supporting both recovery of existing files and rollback of newly created files in the current run.

    File Producer and Consumer Matrix¶

    File Producer Primary Consumer Allowed Update Timing
    requirements_manifest.yaml Initial requirement extraction Planner, design builder, console Append sync when requirement decision changes
    workflow_implementation_plan.md All build stages Subsequent stages, developers Write own marker zone per stage
    workflow_build.yaml Design stage Builder, generators, console Complete central closure before materialization
    config.yaml config generator UCAgent default business process During build or approval of incremental
    eval/*.json Structured storage Console, aggregation, incremental Via controlled CRUD
    applied_changes.json deployer Acceptance, version management Only after successful actual deployment

    This matrix is used to determine "which file should be modified". For example, when tool source code and workflow build spec are inconsistent, editing the registered config alone is insufficient; first decide whether the central design has changed, then rematerialize or fully record deviations with incremental reports.

    Decision Methods for Extended Stages¶

    New stages must satisfy at least one condition: they produce independent, verifiable, subsequently consumed artifacts; they have distinct write permissions; or they isolate high-cost/high-risk actions. Merely because a task description is long is insufficient to split stages. After splitting, calculate the added cost of new references, Checkers, GuideDocs, and context reading.

    Conversely, tool generation and tool testing can be batched in the same responsibility stage: first independently generate multiple tools, then update registration and run comprehensive checks. Splitting each tool into "generate, read-back, check, read-back again" four stages amplifies model round-trips without adding deterministic evidence.

    Failure Paths and Partial Write Analysis¶

    Exceptions in the main build chain may occur during central config loading, path checking, directory creation, template rendering, file writing, Checker materialization, or example copying. Developers should confirm whether each layer of error includes a responsibility-domain error code, and whether the report accurately reflects the writes that have already occurred when failure happens. The Builder is currently not a database transaction spanning all files, so mid-run failure may leave created files; retries depend on overwrite and idempotent recovery by each generator.

    This means new generation steps cannot assume the workflow root is always empty. They should verify existing targets, adopt safe overwrite strategies, and not destroy user drifted files before failure. For shared files requiring overall consistency, such as config registration, generate and validate complete candidates in memory first, then write atomically, rather than appending in a loop and failing on the last item.

    The UCTool wrapper layer should catch known WorkflowBuildError and return code/message/report; unknown exceptions retain traceback for development logs while returning a failure summary without sensitive content to the Agent. Do not catch all exceptions and return ok=True with a warning, as this would face the stage Checker with a half-finished product and cause misleading retries.

    Runtime Contract and Example Targets¶

    runtime_contract connects the build design to the final Makefile. It defines input root, output root, example target, and required input. The Builder uses this to copy test_input to the working workflow example, generate input/output documentation, and let make check_example verify the same contract. If a generator assumes data/ or fixed target names independently, it will diverge from config and documentation.

    When adding new input types, first update the runtime contract and input example manifest, then let the Builder copy actual samples, and finally have the Makefile and Checker read the same list. Example targets must represent real minimal business, not just empty JSON to provide false passes for structural checks.

    Observability and Stage Duration¶

    The process layer should write key artifacts to the report or plan, not just print in the TUI. Long-stage troubleshooting requires knowing the current spec being processed, recent writes, check return codes, and remaining queue. During batch generation, first record total queue count and completed ids; after context compression, resume from structured progress without re-scanning the entire workflow.

    Performance optimization should not eliminate the final comprehensive check. The correct approach is to reduce redundant full checks, limit irrelevant reads, and parallelize non-sharing write tasks. Any optimization should be evaluated by comparing different business scenarios across stage failure counts, tool invocation counts, context compression, and final quality.

    Main Workflow 24 Stages Step-by-Step Explanation¶

    The following stage order comes from the root config.yaml and represents the current parent workflow's public execution architecture. WorkflowPlanAppender spans almost all stages, used to append design records for the current stage only; the table lists only representative tools for this stage. When secondary developers modify stages, they must simultaneously verify config, corresponding Guide_Doc/stages/, implementation plan block, reference/output, and Checker parameters.

    First Group: Requirements and Central Design¶

    Step Primary Purpose Key Artifacts and Checks Secondary Development Notes
    00 extract_requirements_and_plan Convert user guide.md and sample inputs into normalized requirements, input example manifest, and complete implementation plan. Here decide subsequent tools, Checkers, docs, environment, and migration targets; plan detail must exceed user original text. Output requirements_manifest.yaml, input_example_manifest.yaml, workflow_implementation_plan.md; jointly checked by requirements, input example, implementation plan, and living plan Checker. New requirement fields must sync manifest schema, minimal examples, first-stage GuideDoc, Checker, and console parsing. Do not disguise implementation results confirmable in later stages as user requirements.
    01 design_workflow_build_config Form the unique central workflow_build.yaml, organizing directories, public/internal files, runtime contract, tools, business Checkers, GuideDocs, environment, and acceptance into a materializable design. Output central build config and this stage's plan record; WorkflowBuildConfigChecker validates structure and requirement mapping against initial requirements. Modifying central schema is a high-impact change, requiring sync with Builder, four generator types, design editor, and delivery contract. Reference must be specific existing files.

    The core of stage 00 is not "writing three files," but establishing a source of truth that subsequent stages will not arbitrarily redesign. If knowledge base, license, or new config type needs to be added, define the delivery contract here first. Stage 01 converts requirements into fields generators can consume; before adding top-level fields, first judge if existing workflow_spec, runtime_contract, or acceptance can express them, avoiding spec bloat.

    Second Group: Initial Skeleton and Tool Smoke Loop¶

    Step Primary Purpose Key Tools and Checks Secondary Development Notes
    02 build_initial_template Use WorkflowBuilder to create workflow skeleton, environment facilities, internal Checker, central business Checker spec/fixture, and minimal public files in one pass. WorkflowBuildOutputChecker checks 21 initial outputs; requirement coverage prevents skeleton from missing user-required deliverables. When modifying Builder template dispatch, fixed directories, or environment files, update this stage's output list and build regression. Do not supplement files that should be fixed by the skeleton in later stages.
    03 verify_tool_generation_loop Verify that the Tool generator itself can generate source, register, test, and maintain generation state from spec, first opening the general loop before generating business Tools. Use WorkflowToolGenerator; WorkflowToolGenerationChecker checks spec, source, registration, and test loop. New Tool templates or override strategies should be verified with small fixtures here first. Shared registration and generation state must be written serially.
    04 design_smoke_business_tool_spec Select minimal but representative smoke Tools from user business tools, designing real parameters, outputs, errors, and test specs. Output smoke tool spec and plan record; WorkflowGeneratedToolChecker focuses on spec quality at this point. Selected Tools should cover key libraries or input formats but not be complex enough to block the entire parent process. Update smoke baseline semantics when modifying selection rules.
    05 implement_smoke_business_tool Materialize the smoke Tool via WorkflowToolGenerator, proving the parent generator can produce truly importable, registrable business implementations. Output tool source and generation state; Checker validates source, registration, normal/failure calls. Do not allow parent Agent to bypass the generator and write formal source manually. After adding a new renderer, verify template results in this stage, not just renderer string tests.
    06 strengthen_smoke_business_tool_tests Supplement boundary, exception, repeated run, and path safety tests on the initial implementation to prevent "only one happy path" pseudo-passes. Update tool spec, cases, and state; same WorkflowGeneratedToolChecker uses strengthened parameters for stronger coverage. Strengthened tests should change one condition at a time. Avoid requiring all business tools to have unrelated tests when modifying strength thresholds.
    07 initialize_smoke_workflow Integrate minimal workflow config, setup, Makefile, and run targets, perform environment pre-check, and establish a runnable smoke workflow. Use WorkflowEnvironmentPreflight, necessary Tool generation, and ChildWorkflowSupervisor; validate minimal init and environment setup Checker. This connects generation to the runtime environment. New Make targets, environment variables, or proxy strategies must simultaneously update Builder template, schema, GuideDoc, and environment regression.
    08 verify_generated_tools_through_mcp Call generated Tools from UCAgent's actual MCP/adapter boundary, proving they are not limited to Python direct runner usage. Generate MCP test logs/reports; WorkflowMCPToolIntegrationChecker checks registration, calls, and structured results. Must update this stage after modifying adapter, --ex-tools, or MCP parameters. Do not replace MCP integration evidence with ordinary function calls.
    09 freeze_smoke_baseline Form a smoke baseline of the already-passed minimal tools, config, tests, and environment, serving as a stable reference for subsequent full generation. Output smoke manifest and plan record; requirement coverage-like Checker verifies baseline. Baseline only freezes verified facts, should not include all future business tools. Provide old manifest compatibility or migration when modifying fields.

    This group adopts a progressive design: "first verify the generator, then generate one business Tool, then call from real boundaries." During secondary development, do not merge 03, 05, and 08 into a single undiagnosable large stage; do not replicate the full smoke stage for each Tool. Full tools are handled in the batch stage later.

    Group 3: Complete Configuration and All Business Tools¶

    Step Primary Purpose Key Tools & Checks Secondary Development Notes
    10 design_complete_runtime_configs Design final default flows, incremental flows, and optional evaluation configurations based on the central spec, clarifying all variables, stages, GuideDoc injections, and Checker injections. Output config specs and plan records; this phase is primarily guaranteed by the living plan to ensure design additions. When adding a config type, update requirements and the workflow build schema first; prohibit restoring cancelled default/empty configurations.
    11 generate_complete_runtime_configs Generate real YAML using WorkflowConfigGenerator and self-audit placeholders, paths, reference ordering, and registration via WorkflowArtifactInspector. Output config.yaml, config/inc.yaml, etc., and audit logs; WorkflowRuntimeConfigAuditChecker blocks unknown variables and erroneous references. Modifying placeholder rules, stage injections, or file contracts requires updating both pre-generation and post-generation validation in the config generator.
    12 design_all_business_tool_specs Establish a complete spec queue for all business Tools except smoke tests based on requirements and implementation plans. Output tool specs/manifests and plan records. Reuse the interface patterns validated by smoke tests, but each tool must still have business algorithms, exceptions, and tests. Do not skip the generator after writing source code in this phase.
    13 generate_all_business_tools Batch generate all business Tools using WorkflowToolGenerator, coordinating shared registration and state in a single pass. Output tool source code, registration, and generation state. Independent source code can be planned in parallel, while shared config/state is submitted serially. New tools must align with requirements, specs, and docs.
    14 run_full_tool_test_suite Run specs, static imports, direct cases, and MCP integration tests for all tools to form a comprehensive test report. Output tool test summaries; full_mcp_tool_integration_check verifies that not only smoke Tools are tested. When modifying the test runner, retain single-tool location information and the total return code. Do not repeat the full test suite for every generated file.

    10–11 Separate "designing configurations" from "generating and self-auditing configurations" to detect central design contradictions before any formal YAML write. Similarly, 12–14 complete the Tool spec queue first, then batch materialize and integrate tests. If a new business area involves only one Tool, these phases should still retain their semantics, but tasks can quickly confirm there are no additional items rather than generating empty shell files to meet a count.

    Group 4: Documentation, Dependencies, and Reusable Templates¶

    Step Primary Purpose Key Tools & Checks Secondary Development Notes
    15 design_all_document_specs Plan all GuideDocs, user docs, developer source analysis, and dependency descriptions to establish a document spec. Output GuideDoc spec sets; WorkflowGuideDocSpecChecker validates sections, paths, lengths, and coverage. When adding a new document type, update the guidedoc schema, generator, and document regression. FAQ entries should only record cross-business confirmed experiences.
    16 generate_all_documentation_and_dependencies Generate GuideDocs and user docs using WorkflowGuideDocGenerator, while completing requirements/system dependency declarations. Output GuideDocs, docs, requirements; Generated GuideDocs, User Docs, and Dependency Checker perform separate checks. User docs and Agent GuideDocs cannot be mixed in registration. Developer docs must analyze the final real source code; they cannot remain at the plan template level.
    17 generate_all_reusable_templates Generate user-copyable input templates, resource structures, or business reusable files using the controlled template capabilities of WorkflowBuilder. Output reusable template manifest/files and plan records. Templates must originate from requirements and reside in public convention locations; temporary fixtures cannot masquerade as user templates. Unknown template names must be checked before materialization.

    Group 5: Release Completeness and Final Requirement Coverage¶

    Step Primary Purpose Key Artifacts & Checks Secondary Development Notes
    18 complete_readme_and_makefile Summarize final commands, inputs/outputs, environment, tests, and tmux targets to ensure README and Makefile reflect actual delivery. Update README, Makefile, setup-related files, and plans. When modifying Makefile target generation, simultaneously update README, QuickStart, environment schema, and acceptance criteria.
    19 mark_feature_complete Write feature completeness status after all planned features are materialized, prohibiting subsequent masking of omissions with "in planning". Output feature complete manifest/status and plan records. Completion status must derive from actual files and tests, not just phase numbers. New delivery categories must be included in completion calculations.
    20 verify_final_requirement_coverage Re-map final workflow files, tools, Checkers, configurations, and documents back to each user requirement to identify omissions or semantic deviations. Output final coverage; WorkflowRequirementCoverageChecker checks in final mode. When modifying the coverage algorithm, retain the mapping of requirement refs to real files/evidence; do not rely solely on quantity comparison.

    Group 6: Cleanup, Migration, and External Verification¶

    Step Primary Purpose Key Tools & Checks Secondary Development Notes
    21 clean_release_candidate Use WorkflowArtifactInspector to clear temporary logs, browser profiles, caches, and unregistered files, while preserving public delivery and necessary internal tests. Output cleanup reports and plan records. Changes to clean whitelist/keep rules must run the write boundary; never delete eval, res, input, or version history.
    22 prepare_and_verify_migration_packages Build complete or partial migration packages and manifests, verifying paths, dependencies, and allowed contents within the package. Output migration packages, manifests, and check reports; WorkflowMigrationPackageChecker validates generated packages. Partial packages must not accidentally include Tools/Checkers; complete packages must cover environment, docs, examples, and installers. Modifying package formats must provide a version.
    23 verify_migrated_release Unpack, configure, and verify the migrated workflow in an isolated target, rather than just checking compressed file names. Output final migration verification report; similar Migration Checkers verify installation, paths, and tests with final parameters. The verification environment must not rely on absolute paths from the original workspace. When adding new installation steps, update the installer, manifest, and this phase's command whitelist.

    How to Secondary Develop a Phase¶

    1. Confirm the phase's unique responsibility, location, and alias in the root config.yaml.
    2. Modify or add the corresponding Guide_Doc/stages/<index>_<name>.md, providing tools, Checkers, and minimum formats.
    3. If the phase produces new central files, update the wfgen schema, design editor, and implementation plan markers.
    4. In reference_files, list only files existing before the phase; in output_files, list only files actually written by this phase.
    5. Register suitable Checkers; new Checkers follow the generation and regression path described in section 03.
    6. Update living plan rules to ensure this phase only appends its own block.
    7. Add configuration/GuideDoc/phase regression, and verify in a brand new business workspace.

    Do not merely observe if a new phase passes; compare whether the context before and after phases repeats, whether it introduces new full-document reads, or if it can be merged into an existing responsibility domain. Deleting a phase requires cleaning Checker aliases, GuideDocs, plan markers, references, and all old phase assumptions in recovery history.
