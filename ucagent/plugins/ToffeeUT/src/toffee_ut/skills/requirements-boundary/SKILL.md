# 如何定义需求和 DUT 责任边界

## 何时使用、准备什么

新增 DUT、修改功能点或发现越域/漏检时使用。输入是固定版本的需求、微架构合同、真实
实例层次、producer/consumer、生成 RTL、参数与导出端口；不能只拿现有测试名作需求清单。
资料盘点由 `UTProject(action="inspect")` 完成，本方法判断资料代表什么，不重复扫描脚本。

## 怎么做

1. **先写人能理解的行为。** 每项写成“在前提 C 下发生事件 E，应产生结果 R、禁止
   副作用 F，并在合同规定的时间关系内完成”，再列字段。端口/RTL 分支枚举不是功能定义。
2. **双向找遗漏。** 一路从需求、协议和历史缺陷推导行为；另一路从端口、状态变化、异常、
   竞争、失效、复位反查需求。两路对不上时先列缺口，不能按实现反改规范。
3. **沿真实层次分配责任。** 每项标叶块、上层组合、全核或外部环境；子块结果不能被父块
   PASS 替代。跨层行为拆成各层可观察性质，并给出实际交接关系。
4. **核实合法输入域。** 追到 producer 的编码、对齐、互斥、许可、年龄、撤销/不可撤回点。
   协议保证来自当前合同，不凭接口名字追加保持或最终完成约束。生产可达场景与端口压力分开。
5. **逐项选择观察点。** 分别登记输出、状态后果、生成产物中的断言。源码有断言不代表产物
   保留且启用；间接检查须说明盲区。宽度裁剪按[观察点精度](../observation-precision/SKILL.md)
   处理，不把导出位宽变成需求。
6. **处理边界缺口。** 必需端口缺失不能静默补零。先找已有合法观察路径，仍不足时记录
   导出点需求或上层承接，注明位置、状态、关闭条件和影响。移交不等于已经验证，也不授权改 RTL。

## 先建立行为清单，再审查已有 ID

每个 DUT 先说明消费什么事务、维护什么逻辑状态、承诺什么行为、哪些行为由父级或消费者
承接，再按发生条件和后果拆族。预测器的匹配、学习、替换、恢复与队列的入队、唤醒、重放
不能只归成通用 functional/pipeline/stress；测试层级和端口标签不是行为分类。

做两次审查：先由适用合同和 producer/consumer 推导**应有行为**，再用已有功能 ID、模型、
端口/状态转移和用例**反查实现及遗漏**。旧 ID 可落入多个行为族，应有行为也可能还没有 ID
或用例；保留缺口，不为清单全满而删掉它。“全部既有 ID 已归类”只证明资料一致性。

每个行为族给稳定标识、来源条款和依据状态。仅有旧测试标题、计划或 RTL 观察时保持候选；
在设计合同中用 `confirmed` / `inferred` / `open` 区分，格式见 `Guide_Doc/ut-contracts.md`。
分组可按证据调整，不能让自检硬编码标题阻止有依据的重划分。

## 产出

在现有设计/验证规格内维护责任矩阵，不另建状态 JSON：

| 行为 ID / 语义 | 来源版本/条款 | 本层责任与输入前提 | 观察点/禁止副作用 | 上层承接 | 状态与证据 |
|---|---|---|---|---|---|
| 稳定行为标识 | 独立依据或待确认来源 | 叶块/组合及准入条件 | 字段、性质与时序 | 承接位置和实际状态 | 已执行、待执行或残余 |

同时明确单位/地址域、身份、参数、复位、背压、同拍顺序、flush/redirect、异常优先级、可取消
边界和时间保证；不适用项给理由。

## 如何验收

- 从需求抽一项能追到本层检查或明确承接；从端口/状态反查能找到行为归属。
- 合法域有来源；未知编码、缺端口和未承接行为不会自动变成 PASS。
- “本 DUT 不负责”和“当前没有观测到”分开，后者仍是缺口。
- 矩阵是有界范围说明，不是全部硬件已经验证的证明。
