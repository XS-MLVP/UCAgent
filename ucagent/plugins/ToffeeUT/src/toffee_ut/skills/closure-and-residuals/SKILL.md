# 如何制定退出标准并处置残余

## 何时使用、准备什么

开工时制定验收合同，交付时逐项核验，不在全绿后倒推标准。输入为责任/等价类矩阵、需求
追溯、当前结果、checker 自检、已知缺陷和范围约定。

## 怎么做

1. **事先定义退出范围。** 明确 DUT、参数、版本、必验行为、允许的排除和交付要求。
   文档完成、执行完成、功能通过分别判定。
2. **逐项对账。** 每项是已动态检查、不适用（有依据）或残余；分别核对 reached、checked、
   独立 oracle、完成义务和成对控制。填满表不等于语义闭合。
3. **覆盖缺口反馈需求。** 对行、分支、toggle 或功能 bin 的缺口，区分已有功能缺枚举、
   整类行为未定义、当前配置/观察限制；补需求或用例再运行，不只追百分比。
4. **给残余排责。** 写原因、影响、证据、责任层级/承接方、下一实验和阻塞性。“暂未命中”
   或“缺 selector”不证明不可达。宽度裁剪按[观察精度](../observation-precision/SKILL.md)处理。
5. **留下不等于通过。** 尚未证明时先保留，关闭要有消费者合同、结构证明或反例处置；每个
   留项都有关闭条件、承接方和影响。
6. **按原合同决定能否退出。** 必验项未验证、真实 FAIL、未偿还事务义务会阻塞对应硬件
   验收，不能写成 residual 就自动豁免。有限范围交付仅在已有约定允许且如实披露时成立。
7. **冻结结论证据。** 对齐源码、RTL、构建、工具、实际种子使用、nodeid 与同轮覆盖。
   修改后重查受影响项，不重写历史 PASS/FAIL。

## 产出与状态边界

在既有验证规格的范围章节维护：`id / 行为或类 / 缺口类别 / 影响 / 证据 / 承接与下一动作 /
是否阻塞 / 接受依据或待决状态`。真实缺陷进入 `docs/bugs/`，不另建运行前残余 JSON。

- **已执行但依据不足**：可用 `@pytest.mark.uncertain(reason=..., reference=...)` 声明；
  检查仍正常执行，UNCERTAIN 不计 PASS，真实 FAIL/ERROR 优先。引用可选，退出码 0 不表示
  结论通过。
- **未运行、无法观察或无对应场景**：写规格残余，不能制造 UNCERTAIN 用例代替实际验证。
- **用例 INCOMPLETE**：阶段或执行证据不完整，不等于 UNCERTAIN。交付摘要的 INCOMPLETE
  还表示未确认要求、排除范围或覆盖目标等未满足；区分用例状态和整体范围，见
  `Guide_Doc/ut-results.md`。
- **FAIL 的交付**：工作流可以交付有证据、已归因的设计失败，但这不是硬件通过或失败已关闭；
  设施错误必须修复，当前失败不能仅补一条残余就算完成归因。

| 类别 | 处置，不是自动豁免 |
|---|---|
| 未覆盖功能/组合 | 补场景或明确阻塞 |
| 缺观察点/位宽不足 | 找合法检查路径，或移交并保持未验证 |
| DUT 责任之外 | 指明承接层及其真实验证状态 |
| 只有结构/代码线索 | 列候选和动态实验，不称已确认缺陷 |
| 证据不足/环境阻塞 | 留缺失项和重现条件，不称已排除 |
| 明确不适用/范围排除 | 给合同、结构或配置依据及影响 |

## 如何验收

- 每个必验要求有适用运行与比较证据，或明确未完成/阻塞。
- 不用残余登记、旧覆盖配新结果、PASS 数替代 oracle 等手段偷换标准。
- 可声明约定范围达到标准，不能扩成“没有 bug”或“整个系统已验收”。
- 文档改动只验文档，不借历史仿真声称本轮重跑。

报告计数和汇总交给 `UTProject(action="summary")`，本方法审查结论，不重复统计。
证据核对见[归因方法](../triage-and-evidence/SKILL.md)；源历史案例位于
`ucv4xs/docs/lessons/rtl-verification-soundness-20261026.md`（P12）。
