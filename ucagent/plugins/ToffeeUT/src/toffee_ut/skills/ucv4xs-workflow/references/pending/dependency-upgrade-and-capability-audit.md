# 依赖升级与能力核对（待审核）

## 适用场景、准备与授权

版本落后、需要新框架能力、分发名变化，或工具锁可能改变原生缓存身份时参考。先确认
用户是否授权升级；本工作流的 UT 任务本身不授权改锁、卸载包或修改用户旧环境。
安装和版本查询应由既有脚本完成，不在 Skill 添加第二套安装器。

先保留当前安装清单、实际模块位置、源码 commit/本地改动、锁文件和补丁身份，指定新的
结果目录。ToffeeUT 使用自己的一个 venv；发现 Legacy 冲突时拒绝混装并交操作者处理，
不照搬原地卸载或宿主/runner 双环境方案。

## 核对顺序

1. **查实际发布与分发身份。** 安装名、导入名、tag/commit 是不同信息。不能只看 pip list
   就认为读到的文档和导入模块是同一份。源草稿以 uc-toffee 2.1.0 / uc-xcomm 1.1.1 为
   升级例子，不代表本轮已认证这些包的全部行为或每份原生库 ABI。
2. **先决定兼容集合和锁变更，再安装。** 若真实工程有 versions.json、python 约束和
   锁定源码检出，它们必须共同指向所选版本；补丁逐个在干净输入上验证可应用。不能盲升
   构建依赖越过上游约束，也不能以版本号变化假定补丁已生效。
3. **审安装接口与原生身份。** 若源码构建使用规范化分发名的版本变量或 CMake 参数，
   核对它们确实来自所选锁；导入名没变不表示旧/新分发可以共存。原生 ABI、覆盖协议、
   工具路径及库身份可能要求重建，要明确受影响 DUT，不把旧构建 PASS 迁给新工具链。
4. **判断哪些能力真正可用。** 用已有查询/测试入口核对公共 API 和实际行为，区别“入口
   存在”“框架合同成立”“工程适配正确”三个层次。
5. **按风险验收。** 根工具回归、纯模型/组件自检与真实原生回归分开；原生未重建就写
   未验证。没有这次实际执行，不能把源草稿的测试计数或原生收据复制进本轮。

## 能力审查表

| 需求 | 核对的公开入口 | 工程仍负责 |
|---|---|---|
| UNCERTAIN | outcomes 判定及 pytest 标记 | 原因、依据、真实 FAIL 优先 |
| 事务装配与响应检查 | Agent、Scoreboard | 绑定、接受条件、独立模型 |
| 单/多周期激励 | 当前 Driver 模板 | 协议阶段、idle、撤销 |
| 被动采样 | 当前 Monitor | 有效条件、快照、解码 |
| 功能覆盖 | CoverGroupDef / CoverPointDef / CrossDef | bin 语义及实际观察 |
| 原生覆盖 | 真实 managed run 的产物 | 构建、闭包映射与报告口径 |

## 产出与审核标准

记录升级前后版本、分发名、实际检出/本地修订、补丁 hash、ABI/协议查询结果、重建范围、
根回归与实际节点结果。缺原件或未执行明确列出。若仅影响运行时而不影响构建，调整缓存
身份也需独立理由与验证，不能为了避免重建随意剔除工具锁。

源草稿的网络查询、安装和补丁验证命令只在原工程/版本/授权满足时成立；本文保留判断
方法，不把它们作为本工作流默认动作。正式依据仍是当前工具合同和[项目入口](../../SKILL.md)。
