
# 第三项优化：停止重复提交不可恢复的请求

日期：2026-11-10。本项修改 UCAgent 核心的 LangChain 请求与自动循环处理，
对应 ACT4 运行中相同 HTTP 400 被反复重试的问题；不改变 ACT4 工作流的审查规则。
本项已单独转移到基于 main 的分支 `fix/langchain-retry-after-repair`，只包含重试策略修改。

## 原因与修改

原有工具结果恢复逻辑可以给未完成的工具调用补充明确的失败结果，但外层 `loop`
对所有异常都执行相同的重试和等待，缺少“没有恢复进展时立即停止”的判断。

本项先解决这条路径：

- 后端基类提供重试策略接口，默认保留已有有界重试。
- LangChain 在没有工具结果恢复进展时，对 HTTP 4xx 停止自动重试；408、409、429 继续重试。
- HTTP 5xx、连接/超时及未分类运行错误继续使用现有次数和间隔。
- 实际补齐了缺失工具结果时允许继续，让模型处理已经记录的工具失败；之后仍被拒绝且没有新恢复进展时停止。
- 停止前保留原异常链，清理 busy 状态并返回控制台，提示修正请求、配置或对话后再执行 `loop`。
- 不清空对话、不生成成功证据、不推进阶段，不绕过 Check、Complete 或人工授权。

HTTP 状态从异常及其 response、可见异常链中读取，优先采用外层已有的 HTTP 状态，
不根据错误文本猜测。链中循环引用不会导致无限遍历。
工具本身的 HTTP 错误在实际记录失败结果后仍可交给模型处理，不会一律终止整个任务。

## 最小复现与效果

修复前先运行回归用例，确认相同未修复 HTTP 400 的调用次数为 10，而期望为 1。
修复后同一用例通过，无需启动真实模型或运行 ACT4。

使用 `max_loop_retry=10`，并将每次退避分别固定为默认范围的两个端点，离线计数：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 同一未修复请求的模拟调用次数 | 10 | 1 |
| 首次失败后的重复调用次数 | 9 | 0 |
| 固定每次等待 5 秒时的累计退避 | 50 秒 | 0 秒 |
| 固定每次等待 10 秒时的累计退避 | 100 秒 | 0 秒 |

该场景调用次数减少 **90%**，去除 9 次无效重复调用。
旧循环在最后一次失败后仍执行一次等待，因此累计退避按 10 次计算。
这里的等待由计数器模拟，没有实际睡眠，也没有实测网络耗时；不能据此声称完整 workflow 的加速百分比。
